# Blur2ool — Adversarial Engineering Review of SPEC.md + ARCHITECTURE.md

Reviewer lens: ENGINEERING (Swift 6 concurrency, Metal on device and in the Simulator, XcodeGen, frozen interfaces, file ownership, skeleton size, A17 Pro performance at 120 Hz, parity tolerances, blockers for parallel agents).
Date: 2026-10-14. The simulator hold is active (`HOLD-SIMULATOR.md`), so I ran no simctl command and no simulator build. Every check below ran on the Mac (M1 Max, macOS 27.2, Xcode 27.0 27A5194q) or against the iPhoneOS 27.0 SDK.

Each issue gives its severity, where it is, the problem with evidence, and a fix. "Blocker" means the build as planned cannot reliably reach its own acceptance. "Major" means wrong behaviour, false acceptance or a large performance or rework risk. "Minor" means a real defect with a cheap fix. I left out style nits.

## 1. Blockers

### B1. One shared, constantly edited source tree feeds every area's build and tests (blocks parallel agents)
- **Where:** ARCHITECTURE §11.1 rule 2 (mirror the whole repo), §13 rules 1–3, §8 (13 FAM areas write into the single `BlurCore` and `BlurGPU` modules; every App area writes into the single `Blur2ool` module and the single `Blur2oolTests` bundle).
- **Problem:** Every `build.sh` command rsyncs the **whole** live repo. One area's half-finished edit therefore breaks every other area's `core-test`, `typecheck-ios`, `device` and `gpucheck`. Examples are a type used in a file that is not yet saved, or a renamed helper. With 25 agents editing for hours, the tree is broken most of the time, and §13 rule 3 ("wait a minute and retry") does not converge. A second failure mode is name collisions inside the shared modules. Two FAM areas that both declare an internal `struct SATBuilder` or `func clampIndex` in BlurCore, or two test folders with the same file-scope helper, cause a redeclaration error that neither owner can fix alone. §1 bans only bare `Kernel`/`Pass`/`Blur`/`Specimen` names.
- **Fix:** (1) Add `B2_AREA=<AREA>` to `build.sh`. For paths **not** owned by that area, the mirror takes the last version that passed its owner's own checks (a `green/` snapshot each area refreshes with `build.sh publish-green` after its CORE+TYPECHECK pass), or the frozen stub from `Documentation/interfaces/` when no green version exists. Areas then build against stable neighbours. INTEGRATE builds the live tree. (2) Make it a rule: every non-private top-level symbol in `Operators/<G>`, `Pipelines/<G>` and `Tests/*/<AREA>` carries the group or area prefix (`F6…`, `FAMF6_…`), or is nested in a per-group namespace enum (`enum F6 { … }`). Add a `build.sh lint-names` grep to the gate.

### B2. Phone commands lock per command, not per session: agents screenshot each other's builds, and builds hold the lock
- **Where:** ARCHITECTURE §11.1 rule 4 and command table (`device-install` builds and installs under `lockf`; `device-launch` and `device-shot` each lock separately), §11.4 steps 2–5, §8.1 PHONE.
- **Problem:** (a) All areas install the same bundle id, `com.utkarsh.blur2ool`. Between area X's `device-install` and its `device-launch`/`device-shot`, area Y can take the lock and install **its** build, so X records and judges a screenshot of Y's code. Nothing detects this. Under the hold the phone is the only runtime, so this corrupts the only visual evidence. (b) `device-install` runs `xcodebuild` (minutes under a 25-agent load) **inside** the lock, and `device-test` (`xcodebuild test`) builds inside the lock too. Other agents hit the 900 s `lockf -t` timeout and fail. (c) A device build cannot be split from the test run, because the hold guard refuses the command **names** `build-for-testing`/`test-without-building` whatever the destination.
- **Fix:** Add `device-session <script>`, which takes the lock once and runs install → launch(es) → shot(s) → test-without-building for one area. Build outside the lock with new commands `device-build` and `device-build-for-testing` (destination `generic/platform=iOS`, plus the device's id for test products). Stamp the build: write `B2_AREA` and a build UUID into `Info.plist` (`B2BuildStamp`), have the app draw it in a debug-only corner engraving or log it, and have `device-shot` check through `devicectl device info apps` that the installed version matches before capturing. The hold guard should look only at the destination or SDK (`iphonesimulator`, `platform=iOS Simulator`), never at command names.

## 2. Major issues

### M1. Pipeline-state compilation runs synchronously on the main actor (hitches on blur switch, edge change, Trace open)
- **Where:** `GPUBlurPipeline.prepare(_:request:) throws` (sync, `@MainActor`); `GPUContext.computePipeline`/`renderPipeline` (synchronous `makeFunction(name:constantValues:)` and `make…PipelineState`); the seed `GaussianLinearPipeline.prepare` builds only the current edge mode; ARCHITECTURE §5.15 rule 3.
- **Problem:** Function-constant specialisation plus the backend compile happen at pipeline creation. JF §3.1 MEASURED 59–417 ms for the first specialisation on the M1 Max. Edge mode (5 values), direction, trace and half-accumulate are all function constants, so one pass function has up to 40 specialisations. Changing EDGES in the Parameters panel, switching blur, or pushing the Trace therefore compiles on the main thread. Any cache miss inside `encode` compiles mid-render. Crowns and gestures freeze for tens to hundreds of ms. SPEC §2 forbids a spinner, so the freeze is visible.
- **Evidence that the fix is legal:** the SDK marks `MTLDevice`, `MTLLibrary` and pipeline states Sendable. `pso.swift` typechecks both `try await device.makeComputePipelineState(function:)` from `@MainActor` and a `Task.detached` compile that returns a Sendable PSO (Swift 6, strict, iphoneos; MEASURED).
- **Fix:** Make `prepare` `async throws`, and give `GPUContext` `async` `computePipeline`/`renderPipeline` that use the async Metal APIs and coalesce in-flight compiles per cache key. `encode` must never compile: on a cache miss it throws `GPUError.notPrepared`, and the coordinator keeps showing the previous Run with `RENDERING…`. Pre-warm in the background after launch (≥ 10 s, the same idle gate as calibration): the hero dozen's variants × {clamp} × {untraced}. Optionally persist an `MTLBinaryArchive`. Edge modes other than clamp compile on first use, asynchronously.

### M2. Half-resolution preview has no defined meaning in the frozen interface
- **Where:** `OperatorRequest.size` ("447 × 447 for a half-resolution preview"), `RenderQuality.half`, `GPUBlurInputs.quality`, SPEC §4.1.6; nothing in ARCHITECTURE says how parameters change.
- **Problem:** All pixel-unit parameters (σ, r, R, L, offsets, handle centres in window pixels, probe) are expressed at N = 894. The contract does not say whether an operator at `size 447` halves them, or how the half-size input is produced (2 × 2 box? point sample? `generateMipmaps`?). Integer parameters (box r = 1, Kawase offsets in texels, median 3 × 3, sample counts) have no defined half-res equivalent. Thirteen FAM areas will each choose differently, so previews will jump in size or shape when the full render lands, and space-variant centres will move.
- **Fix:** Freeze one rule in Operator.swift. Add `OperatorRequest.pixelScale` (1.0 or 0.5) and `BlurOperator.previewRequest(_:) -> OperatorRequest?`. The default scales every `ParameterUnit.px` and `.position` value by 0.5 and keeps counts. Integers become `max(1, round(x/2))`. `nil` means "this operator has no preview; render full and show `RENDERING…`". The engine produces the half-size input with one documented pass, the `b2_common_downsample2x_fs` 2 × 2 box (SKEL, frozen), and maps the probe and handles by ⌊p/2⌋. Previews are never timed, traced or parity-checked, and the caption says `PREVIEW ½`.

### M3. Parity tolerance scales by the window's global maximum, so it is vacuous on HDR test images
- **Where:** ARCHITECTURE §7 rule 1; `ParityTolerance.allowance` and `ParityRunner.run` (`scale = max over all window pixels`).
- **Problem:** Night City has lights of 100 (6,400 at +6 EV; SPEC §11). With `bilinear` and 2 passes the allowance is (2⁻²⁰ + 2·2⁻¹⁰)·scale = **0.195 at 100** and **12.5 at 6,400** linear units, **on every pixel**, including the dark buildings at 0.02–0.06. A kernel that drops half its taps passes on Night City, which is the default test image of F3, F4, F6 and F11 (SPEC §9.4). Even `exactF32` grants 100·2⁻²⁰ ≈ 10⁻⁴ absolute at 0.02. That is fine, but it shows the scale is global.
- **Fix:** Use a **local** scale: `scale(p) = max(1, max |input| over p's support)`. Compute it with a separable running-max (van Herk) over the support radius the operator declares, or with a new `PassPlan.supportRadius`; global and FFT operators fall back to the global max. Add **mutation tests** in GPUCHECK: for every tolerance class, a deliberately broken pipeline (last tap dropped, weights × 1.01, one pass skipped) on Night City at +4 EV must FAIL. GPUCHECK's acceptance already has one wrong-reference test. Extend it to one per class and per HDR specimen.

### M4. Device-dependent hardware rules are hard-coded from the M1 Max, and the "Simulator" evidence is not independent
- **Where:** `ReferenceOptions.parity` (`subTexelBits: 8`), ARCHITECTURE §4.3 and §7 rule 2, SPEC §6.4 item 5, the pyramid CPU references (2 × 2 box `generateMipmaps`), in-app PARITY telemetry (§7 rule 7).
- **Problem:** (a) Research §2.7 item 2 itself MEASURED that the Simulator "evidently forwards to the Mac GPU". So "8 bits, MEASURED on the M1 Max **and the Simulator**" is one measurement, not two. (b) The rounding rule (round to nearest at 1/256) is assumed, not parameterised: `ReferenceOptions` has a bit count but no rounding mode. (c) Nothing connects This phone's `DeviceProbeResult` (sub-texel bits, mip filter) to the `ReferenceOptions` the in-app parity uses. If the A17 Pro quantises differently (bits or rounding are UNVERIFIED), the CPU emulation is wrong by up to 1/128 of the local contrast per fetch. The `bilinear` allowance of 2⁻¹⁰ per pass is then exceeded, and the app prints "GPU differs from the math" on every settled Run of every linear-sampled or gather blur, starting with the Bench default. (d) `generateMipmaps` is "may vary by feature family" (Apple docs, research §3.5), yet the mip-chain reference assumes a 2 × 2 box.
- **Fix:** Add `subTexelRounding: .nearest | .truncate` to `ReferenceOptions`, and a `ReferenceOptions.forDevice(_ probes: [DeviceProbeResult])` factory. In-app parity uses it, and until the sub-texel probe has run on this phone, the bilinear classes report PARITY as `reportOnly` with the caption `SUB-TEXEL RULE NOT YET MEASURED`. Run the sub-texel probe automatically once, in the background, after the idle gate (it is a ~1 ms dispatch). Implement the mip chain with an explicit 2 × 2 downsample shader instead of `generateMipmaps`, so the reference is device-independent; keep `generateMipmaps` only as a This phone probe. Record the A17 values in §11.6 as gate inputs for INTEGRATE.

### M5. No cost budget: worst-case parameters produce 0.1–1 s command buffers, then 18 timed repeats
- **Where:** SPEC §9.4 ranges, §4.1.6 (half-res preview, "3 warm-ups + 15 timed"), §10.1; ARCHITECTURE §5.10 RenderScheduler; no per-entry budget anywhere.
- **Problem:** Fetches per frame at N = 894 (0.80 MP), COMPUTED from SPEC's ranges:

  | Entry at range limit | Fetches per pixel | Fetches per frame | MODELED A17 Pro time* |
  |---|---|---|---|
  | `disc-blur` Gather, R = 64 | π·64² ≈ 12,868 | 1.0·10¹⁰ | ≈ 0.7 s |
  | `polygonal-bokeh` 5 blades (2-D gather), R = 64 | ≈ 9,700 | 7.8·10⁹ | ≈ 0.5 s |
  | `nonlocal-means` patch 7, search 21 | 21² × 7² = 21,609 | 1.7·10¹⁰ | > 1 s |
  | `gaussian-2d-direct` σ = 8 | 2,401 | 1.9·10⁹ | ≈ 0.1 s |
  | `heat-equation` t = 200, λ = ⅛ | 1,600 iterations × 5 | 6.4·10⁹ plus 1,600 passes (≈ 20 GB of traffic) | ≈ 0.3–0.4 s |

  *MODELED by scaling research's MEASURED M1 Max gather rate (64-sample bokeh on 3.6 MP in 2.96 ms ≈ 78·10⁹ fetches/s) by the research's own ≈ 5× A17 Pro factor (≈ 15·10⁹ fetches/s). UNVERIFIED until This phone measures it.

  Half resolution only divides this by 4 (and the radius halves, so O(r²) gathers drop by 16). The settled full render, followed by 18 timing command buffers, then keeps the GPU saturated for **≈ 10–20 s** after every finger lift on these entries. That costs heat and battery, competes with the render server for the GPU, and keeps showing `RENDERING…`. Timing is not specified as cancellable, so a new touch waits behind the queue. Whether iOS 27 kills a ≥ 1 s command buffer (`MTLCommandBufferError` timeout or "impacting interactivity") is UNVERIFIED.
- **Fix:** (1) Add `PassPlan.fetchesPerFrame` (already derivable) and a frozen budget table: preview ≤ 2·10⁸ fetches (≈ 13 ms MODELED), full ≤ 2·10⁹. Above the preview budget the preview drops to ¼ resolution. Above the full budget, `resolveVariant` switches automatically (disc → row-span SAT, 2-D Gaussian → separable, NLM search capped at 11) with the reason in the status row, or the range ends there. (2) Timing becomes budgeted and cancellable: stop after 15 samples **or** 1.0 s of summed GPU time (minimum 3 samples, `n` shown). Every touch cancels between command buffers. Skip timing above the full budget with `TOO SLOW TO TIME · ≈ x ms MODELED`. (3) Split full renders above about 50 ms into horizontal bands, one command buffer each, so the compositor keeps getting GPU time.

### M6. CPU references: in-app parity recomputes the full window on every settle, on the main actor in the CLI, at -Onone in Debug
- **Where:** `BlurOperator.referenceCrop` default (full reference, then crop); `ParityRunner` is `@MainActor` and calls `BlurReference.run` inline; ARCHITECTURE §7 rule 7 (every settled Run); §3.2 (gpucheck at 256 **and** 894 for every case).
- **Problem:** At default and range-limit parameters, a full 894² Double reference is ≈ 7·10⁹ operations for brute bilateral, about 10¹⁰ for NLM, and 6·10⁹ for heat at t = 200. That is seconds to minutes per settle on the phone, on one core, and 100× worse in Debug (M7). The CPU load runs **concurrently with the 18 timing buffers** and skews them thermally. In gpucheck the references run on the main thread one case at a time, so a full INTEGRATE/QA run (62 entries × variants × edge modes × sRGB/straight × 2 sizes) becomes hours long and is re-run by every gate.
- **Fix:** (a) Make `referenceCrop` with an apron **required** (no default) for every operator whose `costClass.isHeavyByDefault`. Only global operators (FFT, IIR) may compute the full window. (b) Split `ParityRunner.run` into a `@MainActor` GPU half and a `nonisolated` CPU half run in `Task.detached`. Parallelise references over row bands with `DispatchQueue.concurrentPerform`, which is pure and deterministic, so the result is identical. (c) gpucheck runs the full window only at 256. At 894 it checks a 128² crop at the case's probes. (d) In the app, parity runs only **after** timing completes, at background priority, and is cancelled by a new generation.

### M7. Debug builds of BlurCore/BlurGPU run at -Onone, and the canvas conversion runs on the main actor
- **Where:** `project.yml` (no optimisation override); `GPUContext.upload` (`image.pixels.map { SIMD4<Float16>($0) }` on `@MainActor`); §11.4 installs **Debug** for every phone screenshot and `device-test`.
- **Problem:** MEASURED: converting the 1406² canvas takes **444.6 ms at -Onone** against 3.5 ms at -O. Every specimen change, photo import and first launch therefore freezes the main thread for about 0.5 s in the builds agents judge. Canvas generation and CPU references are also about 100× slower. Phone acceptance (the first ten seconds, the `settle=1` scenarios, "GPU chip MEASURED after settle") is judged on a build that is not representative.
- **Fix:** In `project.yml`, set `SWIFT_OPTIMIZATION_LEVEL: -O` for the `BlurCore` and `BlurGPU` targets in **all** configurations (keep `-Onone` for the app target, so it stays debuggable), and `-c release` is already used for gpucheck. Move the fp16 conversion into BlurCore (`ImageBuffer.halfBytes() -> Data`, Sendable) and run it in the detached canvas task. `upload` then takes `Data`.

### M8. Exposure is a canvas option: every EXPOSURE crown detent regenerates and re-uploads a 1406² canvas
- **Where:** `SpecimenOptions.exposureEV` (Specimens.swift); `ParameterScope.specimenExposure` (the EXPOSURE crown of deck C for `exponential-blur` and `lorentzian-blur`); SPEC §11 rule 5.
- **Problem:** A crown detent, rate-limited to 20 per second, triggers canvas generation (31.6 MB of Float) plus `upload`. That is about 0.5 s on the main actor in Debug (M7) and a 16 MB staging buffer and blit even in Release. The EXPOSURE crown cannot feel like a crown.
- **Fix:** Make exposure a render-time factor of 2^EV. Apply it in the window step (replace the blit `encodeWindowCopy` with a copy fragment pass that multiplies, or a separate multiply pass) and in `BlurReference.run`, as `input × 2^EV` before `roundedToHalf`. Power-of-two scaling commutes exactly with fp16 rounding, barring overflow and subnormals (fp16 max 65,504 > 100·2⁶), so parity is unchanged. The canvas is generated at 0 EV only.

### M9. Pipeline instances, their scratch textures and the "pass intermediates" are shared and overwritten
- **Where:** `GPUBlurPipeline` (scratch "owned by the pipeline instance and reused", §5.8 rule 5); seed `GaussianLinearPipeline.scratch`; `EncodedBlur.intermediates` ("kept so the Algorithm floor and Trace can show each pass"); `RenderCoordinator.displayTexture(slot:pass:)`.
- **Problem:** Nothing says how many pipeline instances exist. If the coordinator caches one per (blur, variant), then (a) Compare on the Precision or Space axis, Line-up and ABAB timing render the **same** blur and variant in two slots through one scratch texture, and (b) every later encode, including the 18 timing runs, overwrites `mid`. The periscope's `PASS 1 OF 2`, the Algorithm floor's pass tiles and the Trace's "9 × 9 from the real intermediates" then show a texture from a **different execution** than the acknowledged Run. That breaks SPEC §6.4 items 2 and 4.
- **Fix:** Freeze it: one pipeline instance per **(slot, blur, variant)**, and `EncodedBlur.intermediates` are valid until the next `encode` on that instance. The coordinator keeps a separate *display* instance per slot and uses a *timing* instance for timing and parity, so measurement never touches displayed intermediates. Trace and periscope readbacks are taken from the traced display render before any other encode on that instance.

### M10. Compute-tile and 2-D-direct fixtures contradict the binding rules
- **Where:** SPEC §5.3 A floor 6 (compute tile: probe = thread 190 of threadgroup (1, 300), SIMD-group 5 lane 30, **3,072 B**); SPEC §9.4 Gaussian (`TILE BUDGET R ≤ 56`; 2-D direct "disabled above σ 8"); SPEC §8.5 P4 ("3,721 vs 122 taps **at σ 10**"); ARCHITECTURE §4.4 rule 2 ("2-D image kernels use **16 × 16** threadgroups"), §6.3 rule 8 ("never a hard-coded" tile size).
- **Problem:** The fixture is research's **256 × 1** row tile with 3,072 B of *static* memory sized for a hard-coded MAX_R = 64 (gpu-pipeline §3.2). That contradicts the 16 × 16 rule and the no-hard-coding rule. "R ≤ 56" matches a third geometry: a 16 × 16 group with an x-only apron, (16 + 2·56)·16·8 B = 16 KB. Under the 256 × 1, MAX_R = 64 design the cap would be 64. FAM-F2 cannot satisfy the fixture, the rules and the budget at once. Separately, P4 asks for the 2-D direct variant at σ 10, which §9.4 disables. Its 3,721 taps would also overflow the trace (M11).
- **Fix:** Bind the 256 × 1 row tile, which is the only one with a fixture. Allow `dispatch2D(preferred: 256 × 1)` for 1-D tiles in §4.4 rule 2. Use dynamic threadgroup memory of (256 + 2r)·8 B, so r = 12 gives 2,240 B, not 3,072. Define the budget as r ≤ (min(16 KB, device limit)/8 − 256)/2 = 896 on 16 KB (the Gaussian then effectively never falls back), or state a different binding cap with its derivation. Update SPEC §5.3 A's "3,072 B" to the computed value. Move P4 to σ 8 (2,401 vs 98 taps), or raise the 2-D limit to σ 10 for the lesson only.

### M11. Trace capacity is a fixed 1,024 taps: false parity failures and silently truncated "full" traces
- **Where:** `TraceRequest.maxTapsPerPass = 1024` (default); `ParityRunner.run` uses `TraceRequest(probe:)` and checks `blocks.last?.taps.last?.runningSum` against the output; SPEC §10.2 (Tier 1: "every fetch / tap").
- **Problem:** Any traced pass with more than 1,024 taps overflows. The last *recorded* running sum is then a partial sum, `finalSumMatchesOutput` is false, and the case FAILs. Affected: `gaussian-2d-direct` at σ > 5.0 (r = ⌈3σ⌉ = 16 gives 1,089 taps; 2,401 at σ 8), `disc-blur` gather at R ≥ 19 (π·19² ≈ 1,134 taps), polygonal 2-D gather at large R, and NLM. In the app, the same default truncates the Tier 1 Trace that SPEC promises is complete. The final-sum rule also does not cover kernels whose output is not the last running sum: bilateral divides by Σw, median selects, and Kuwahara picks a sector.
- **Fix:** Size the capacity from `op.passPlan(request).passes[p].tapsPerPixel` (+1 for a final record), per pass, both in ParityRunner and in the app's TraceSession. Require every traced pass to write a final record (`flags = 2`) holding the value it stores. The final-equals-output check reads that record, never `taps.last`. The check is valid only when `overflow == 0`.

### M12. Wave-1 areas depend on a function that another wave-1 area has not yet written
- **Where:** ARCHITECTURE §6.1 last paragraph: F4 (Lorentzian sum of Gaussians), F10 (materials), F11 (bloom, drop shadow) and DoG use `b2_f2_gauss_separable_fs`, which FAM-F2 adds in wave 1.
- **Problem:** `metal-check` passes, but until FAM-F2 lands that function, those areas' pipelines fail at `makeFunction` and their PARITY cannot pass. Each also writes its own Swift encode for a function whose bindings it cannot test yet.
- **Fix:** SKEL writes `b2_f2_gauss_separable_fs` (integer taps, renormalise-capable, about 25 lines) next to the linear seed. Add a frozen helper in `Sources/BlurGPU/Core/GaussianPassEncoder.swift` (encode one H or V Gaussian pass from a `Kernel1D` into a target), so other groups never depend on FAM-F2's internals.

### M13. The walking skeleton proves only one GPU pattern (two fragment passes)
- **Where:** ARCHITECTURE §9.1 item 4 (only `GaussianLinearPipeline`).
- **Problem:** Several frozen paths are exercised for the first time by ten or more areas at once: `dispatch2D` with dynamic threadgroup memory, compute outputs with `.shaderWrite`, TRACE_PROBE in a compute kernel, MRT render passes (polygonal bokeh), mip chains with `readTexels(level:)`, auxiliary textures, device-buffer FFT planes, and `.commandBufferPerPass` timing. Any flaw (for example M11 or the post-pass attribution in m1) is found ten times in parallel, and each finder files a frozen-file request mid-wave.
- **Fix:** Add two small seeds to SKEL, each with parity cases that run with `--apple2-limits`. First, `gaussian-compute-tile` (256 × 1 tile, dynamic memory, traced). Second, a two-attachment MRT pass, the first pass of `polygonal-bokeh` with a CPU reference. Also add one `.commandBufferPerPass` timing smoke test on the Mac GPU. That is roughly a day more for SKEL and saves many wave-1 round trips.

### M14. Test filters select the wrong tests
- **Where:** §8 ("`core-test --filter <TAG>` runs exactly one area's tests"), §12.3 (`device-test -only-testing:Blur2oolTests/<AREA>`).
- **Problem:** (a) `swift test --filter` is an unanchored regex over `Module.Class/method`. `--filter FAMF1` also runs `FAMF10_*` and `FAMF11_*`, so FAM-F1's CORE fails whenever F10's or F11's in-progress tests fail. (b) `-only-testing:` takes `Target/Class[/method]`, not a prefix. `Blur2oolTests/FAMF2` matches no class (classes are `FAMF2_<Name>`), so the area's phone tests either do not run at all or error out; which of the two happens is UNVERIFIED for Xcode 27.
- **Fix:** (a) `build.sh core-test --area <TAG>` passes `--filter '\.<TAG>_'`. (b) `device-test --area <TAG>` lists the test classes with `<TAG>_` prefixes from `Tests/AppTests/<AREA>/*.swift` and passes one `-only-testing:Blur2oolTests/<Class>` per class. It fails if the list is empty or the result bundle reports zero executed tests.

### M15. `GPUContext.dispatchLog` grows without bound in the app (frozen file)
- **Where:** `GPUContext.dispatch2D` appends a string on **every** compute dispatch, forever.
- **Problem:** Iterative entries dispatch hundreds to thousands of passes per render: heat at t = 200, λ = ⅛ is 1,600 iterations, and Perona–Malik is up to 500. At about 70 B per entry and 20 renders per second while dragging, that is about 0.7–2 MB/s, roughly 40–130 MB per minute of interaction, never freed.
- **Fix:** `public var recordsDispatches = false` (set true by gpucheck and tests), or keep a ring buffer of the last 4,096 entries.

### M16. Rank-exact tolerances cannot pass with the colour or alpha passes that every group must test
- **Where:** §5.8 ("the sRGB-encoded and straight-alpha paths at least once per group"); `rankExact` (bit-exact); `b2_common_colour_fs` (fast-math `powr`, fast division in `b2_unpremultiply`) vs `ColourTransform` in Double.
- **Problem:** The GPU pre-pass encodes in fast math, so its fp16 values can differ by 1 ulp from the CPU's Double encode rounded to half. The median, morphology or Kuwahara result then differs by 1 ulp, the post-pass amplifies it, and `bitExact` fails. FAM-F8A, F8B and F9 must include such a case, so they cannot meet their acceptance.
- **Fix:** In `ParityEvaluation.evaluate`, when `ColourTransform.needsPasses(settings)` holds, combine the case's class with `.fastMath` automatically, with `bitExact` dropped. Alternatively, have `BlurReference.run` take the GPU's own pre-pass output as the reference input for rank classes, so selection is compared on identical values.

## 3. Minor issues

- **m1. Per-pass timing folds the colour post-pass into the last blur pass.** `GPUCommandRecorder.commandBuffer(forPass:)` returns the current buffer for negative indices. In `.commandBufferPerPass` the post-pass (−1) therefore lands in the last blur pass's command buffer, and `passMilliseconds` reports it as part of that pass in sRGB and straight modes. Fix: give negative indices their own untimed buffer when isolating.
- **m2. The drawable size is not pinned.** `MetalSpecimenView.makeUIView` leaves `autoResizeDrawable = true`. A 297.99-pt layout then gives an 893-px drawable, and the 1 : 1 nearest present silently resamples. Fix: `autoResizeDrawable = false`, `drawableSize = N × N`, `contentScaleFactor = displayScale`, `layer.colorspace = sRGB` (§4.1), and assert in a phone AppTest.
- **m3. The "≤ 16 ms main-actor slices" for SwiftUI calibration cannot be enforced.** One `ImageRenderer` render is synchronous and cannot be pre-empted, and the first one compiles RenderBox pipelines. Fix: specify "one render per run-loop turn, measured. If a render exceeds 16 ms, back off ×2 and record it", and allow no render while `controlActive`.
- **m4. Cross-platform canvas determinism is asserted but tested only on the Mac.** SPEC §11 rule 1 and ARCHITECTURE §5.6 say "bit-identical on every platform", but TESTIMAGES only compares two Mac runs. Generators that use `sin`, `exp` and `log` depend on each OS's libm (UNVERIFIED identical across macOS 27.2 and iOS 27). Fix: an AppTests case on the phone that hashes canvases and compares them with the Mac hashes recorded by TESTIMAGES. Alternatively, generators use only +, ×, √ and BlurCore's own polynomial transcendental functions.
- **m5. gpucheck validates the source, not the app's binary path.** The CLI compiles one translation unit with the macOS runtime compiler. The app ships Xcode's per-file offline compile for Apple9. Traced = untraced bit-exactness and fast-math behaviour could differ between those front ends (UNVERIFIED). Fix: add `gpucheck --metallib`, which builds a macOS metallib with `xcrun -sdk macosx metal -fmetal-math-mode=fast -fmetal-math-fp32-functions=fast` per file plus `metallib`, the same split and flags as Xcode. Run both modes in GATE and INTEGRATE.
- **m6. `requests.md` is one file that 25 agents append to concurrently,** so read-modify-write updates get lost. Fix: `Documentation/build/requests/<AREA>.md`; INTEGRATE reads the folder.
- **m7. "First frame rendered before the window appears" (SPEC §2) has no mechanism.** Rendering is async, and a synchronous wait on the main thread would block launch. Fix: SPEC allows the housing to show the sharp INPUT canvas (a real image, not a placeholder) until the first Run is acknowledged, typically within one or two frames, with no spinner.
- **m8. The probe readback is a second command buffer and await per acknowledged frame.** Fix: `RenderCoordinator.render` encodes the 1-texel blit into the render's own recorder before committing (one completion).
- **m9. `encodeFullBlur` allocates two fresh window-sized textures per render in sRGB or straight mode** and never recycles them. That is about 13 MB of allocation per detent. Fix: recycle `pre` and `blurred` to the pool after completion, or keep them per slot.
- **m10. TRACE_PROBE in fragment passes needs fragment-stage device-buffer writes.** These are UNVERIFIED for the Simulator's reported Apple2 family (research §2.7 shows the Simulator forwards to the Mac GPU, but Apple documents Apple2 limits). Fix: put a traced fragment pass in the first post-release `sim` check (`deferred-by-hold.md`). If it fails, fall back to the compute-traced variant for the Trace in the Simulator only, with both branches compiled for device per §12.3.
- **m11. `typecheck-ios` cannot see Xcode-generated asset symbols** (`Color(.name)`, `ImageResource`), so code using them passes `device` but fails the fast pre-flight, or the reverse. Fix: `ASSETCATALOG_COMPILER_GENERATE_ASSET_SYMBOLS: NO` in `project.yml`, and a rule: no asset symbols, because tokens live in code.
- **m12. Signed `device` builds in 25 parallel agents.** `-allowProvisioningUpdates` with automatic signing in every compile check risks keychain or provisioning contention. That risk is UNVERIFIED, and signing adds nothing to a compile check. Fix: `build.sh device` adds `CODE_SIGNING_ALLOWED=NO`; only `device-build` and `device-install` sign. I MEASURED that an unsigned `generic/platform=iOS` build of an XcodeGen app with frameworks succeeds.

## 4. Things checked and found sound

- **Swift 6 isolation model.** `SWIFT_DEFAULT_ACTOR_ISOLATION: nonisolated` with explicit `@MainActor` on GPU and engine types matches the SDK. `MTLTexture`, `MTLBuffer` and `MTLCommandBuffer` are not Sendable and stay on the main actor. Device, library, queue and pipeline states are Sendable (so M1's fix is legal). `MTKViewDelegate` is UI-actor-annotated, so `@MainActor PresentRenderer` conforms cleanly. The continuation completion pattern is fine.
- **XcodeGen and build settings.** `MTL_MATH_MODE: FAST` is valid, and `MTL_MATH_FP32_FUNCTIONS` defaults to FAST with `MTL_FAST_MATH: YES`, which matches gpucheck's `.fast`/`.fast`. `Package.swift` next to the generated `.xcodeproj` does not confuse `xcodebuild`. An `Info.plist` inside `App/` is not copied as a resource. Portrait-only plus iPhone-only builds with no orientation warning. `basedOnDependencyAnalysis: false` avoids the run-script "no outputs" warning.
- **Metal ABI.** `B2TraceHeader`/`B2TraceTap` (32/64 B) match `TraceLayout.Header`/`Tap` field for field (SIMD4<Float> aligns to offset 16 in both). The edge index mapping matches the samplers (`mirrored_repeat` repeats the edge texel). Include guards make the one-TU concatenation safe.
- **`exactF32` tolerance (1 ulp16).** My fp32-vs-fp64 simulations never exceeded 1 fp16 ulp, for separable σ 1–12 with fp16 intermediates and for 2-D σ 8 including HDR lights (§0).
- **Simulator rules.** The design already bans sRGB render targets, read-write textures, Metal 4, hard-coded 1,024-thread groups and `getBytes` on mip levels, and emulates Apple2 limits in gpucheck. Under the hold this is the right substitution, except for m10.
- **Timing method.** Stage-boundary counters where supported, otherwise one command buffer per pass; nil in the Simulator; fragment rather than compute for compressible outputs. All consistent with research §2.6 and §5.
